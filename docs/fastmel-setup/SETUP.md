## 1. Images

The MIMIC authors publish the images as three password-protected OneDrive
links (password `kdd2023`), as **uncompressed .tar** files:

| Archive | Size |
|---|---|
| `WikiMEL.tar` | 2.96 GiB |
| `RichpediaMEL.tar` | 2.63 GiB |
| `WikiDiverse.tar` | 1.80 GiB |

`download_mimic_images.py` handles all of it and **is checkpointable at every
stage** — Ctrl-C whenever, re-run the identical command to resume:

```powershell
cd c:\Users\user\Desktop\kmpooja\thirdSem
python mimic-image-downloader\download_mimic_images.py --dataset all
```

Stages, each recorded independently in `mimic-dataset-archives/download-checkpoint.json`:

1. **download** — clears the SharePoint ASP.NET password gate automatically, then
   streams to `<name>.tar.part`. The server answers `206 Partial Content`, so
   resume is real: a re-run sends `Range: bytes=<already have>-` and continues
   rather than restarting. Checkpoint is fsync'd every 16 MiB. Dropped
   connections and expired auth cookies are retried automatically (up to 12
   attempts, re-authenticating each time and resuming from the `.part` file) —
   a multi-GB transfer routinely outlives the `FedAuth` cookie.
2. **verify** — confirms the file is a readable tar (catches the classic failure
   where an HTML error page got saved under a `.tar` name), records sha256.
3. **extract** — unpacks member by member. Resume is driven by *what is on disk*
   (a member already present at the right byte size is skipped), so an
   extraction killed midway through a file is redone rather than left truncated.
4. **unpack** — each `.tar` holds only ~9 members: the JSON metadata plus the
   images bundled as **separate nested zips** (`kb_image.zip`,
   `mention_image.zip`). This stage unzips them in place, with the same
   size-based resume rule. The zips already carry the correct top-level folder
   names, so this lands exactly where the configs point.
5. **arrange** — normalises the top-level directory to the dataset name and
   reports the `kb_image` / `mention_image` file counts.

Each `.tar` also ships the authoritative `qid2id.json`. The copy generated by
`generate_qid2id.py` was compared against it for WikiMEL and is **identical**,
so either source is fine.

Other commands:

```powershell
# progress across all datasets
python mimic-image-downloader\download_mimic_images.py --status

# one dataset only
python mimic-image-downloader\download_mimic_images.py --dataset WikiDiverse

# start one over from scratch
python mimic-image-downloader\download_mimic_images.py --reset WikiMEL
```

### Downloading by hand instead

If the automated path breaks (the share links are a third party's OneDrive and
could change or rate-limit), download the three `.tar` files yourself from the
links in the [MIMIC readme](https://github.com/pengfei-luo/MIMIC), drop them in
`mimic-dataset-archives/`, and run:

```powershell
python mimic-image-downloader\download_mimic_images.py --manual --dataset all
```

`--manual` never touches the network; it picks the archives up from disk and
runs verify → extract → arrange on them. Same checkpoint, so the two modes are
interchangeable mid-run.

The script is **stdlib-only** — it does not need the venv.

## 2. Environment

The repo's pinned `requirements.txt` cannot be used on this machine, for a
reason that is not negotiable:

> `torch==1.11.0+cu113` is built for CUDA 11.3, which has **no sm_89 kernels**.
> An RTX 4090 is sm_89. That wheel physically cannot run here, on any Python
> version. CUDA 11.8 is the earliest toolkit with Ada Lovelace support.

`local-configs/requirements-adjusted.txt` documents every deviation inline. The
short version:

| Pinned | Used | Reason |
|---|---|---|
| `torch==1.11.0+cu113` | `torch==2.0.1+cu118` | sm_89 support |
| `pytorch-lightning==1.7.7` | `==1.9.5` | last 1.x line, validated against torch 2.0, still has the 1.x hooks and `Trainer(amp_backend=...)` this repo uses — both **removed** in PL 2.0 |
| `transformers==4.18.0` | `==4.30.2` | 4.18 won't load on modern torch; 4.30.2 still exposes `CLIPProcessor.feature_extractor`, which `dataset.py` calls |
| — | `numpy==1.24.4` | torch 2.0.1 is built against the numpy 1.x ABI |

Python 3.8 (what the authors used, per the `cpython-38` `.pyc` leftovers) is not
installed here and would not help — the CUDA constraint is what forces the
change, not the Python version.

```powershell
python -m venv fastmel-python310-venv
.\fastmel-python310-venv\Scripts\python.exe -m pip install -r local-configs\requirements-adjusted.txt
```

## 3. Repo fixes

### `qid2id.json` was missing entirely (blocker)

Every config points `data.qid2id` at `data/<Dataset>/qid2id.json`, and
`DataModuleForMIMIC.__init__` opens it before anything else — but the file is
not in the repo. `FASTMEL-reproduction-notes.md` did not catch this.

It is fully derivable: `kb_entity.json` carries both `qid` (the Wikidata id the
mention files reference) and `id` (the dense row index). Regenerate with:

```powershell
python mimic-image-downloader\generate_qid2id.py
```

All three datasets map cleanly onto a contiguous `0..N-1` range:

| Dataset | Entities | id range |
|---|---|---|
| WikiMEL | 109,976 | 0..109,975 |
| RichpediaMEL | 160,935 | 0..160,934 |
| WikiDiverse | 132,460 | 0..132,459 |

`dataset.py` reads this with `json.loads(f.readline())`, so the generator writes
the whole mapping on one line.

### `codes/model/lightning.py` — two blockers

Both would have stopped the very first `python codes/main.py`:

1. **Line 30 was a `SyntaxError`.** Upstream shipped
   `self.score_function = cosine_similarity if args.score_function == "cosine"`
   — a ternary with no `else`. The module could not be imported at all.
   Replaced with an explicit `if/else` that raises on any non-`cosine` value.
2. **Line 10 imported a module that does not exist:**
   `from codes.model.model_late_int import LateEncoder`. `model_late_int.py`
   is a leftover reference to the authors' private codebase. It is only used
   when `model.pooling_type` is empty (the late-interaction variant), which no
   shipped config selects, so the import is now lazy and only fails if that path
   is actually requested.

`git -C fastmel-source-repo diff` shows exactly this and nothing else.

### `python codes/main.py` does not work as documented

The README's `python codes/main.py --config <path>` fails immediately with
`ModuleNotFoundError: No module named 'codes'`. Running a script puts *that
script's* directory (`codes/`) on `sys.path`, not the repo root, so the
`from codes.utils.functions import ...` imports cannot resolve. Upstream MIMIC
worked around this in its `run.sh`; this repo dropped the shell script and never
updated the instructions.

Set `PYTHONPATH` to the repo root before running — the commands in
[section 4](#4-running) do this.

### `num_entity` was wrong for RichpediaMEL

Shipped config says `160933`; the KB actually holds `160935`. It only worked by
luck — `_step()` computes `ceil(num_entity / eval_chunk_size)`, and with
`eval_chunk_size: 6000` the rounding happened to cover the tail. A different
chunk size would have silently truncated the candidate pool. Corrected in
`local-configs/richpediamel_local.yaml`.

## 4. Running

Paths in `local-configs/*.yaml` are absolute, so the working directory only has
to be the repo root (for the `codes.` package imports).

`PYTHONPATH` must point at the repo root (see the section above).

**Smoke test first** — 1 epoch, 8 train batches, `num_workers: 0`:

```powershell
cd c:\Users\user\Desktop\kmpooja\thirdSem\fastmel-source-repo
$env:PYTHONPATH = "c:\Users\user\Desktop\kmpooja\thirdSem\fastmel-source-repo"
..\fastmel-python310-venv\Scripts\python.exe codes\main.py --config ..\local-configs\wikimel_smoke.yaml
```

Then a full run:

```powershell
..\fastmel-python310-venv\Scripts\python.exe codes\main.py --config ..\local-configs\wikimel_local.yaml
```

### Running detached, for a multi-hour job

A full run outlives most terminal sessions, so launch it as an independent process
and log to disk:

```powershell
$root = "c:\Users\user\Desktop\kmpooja\thirdSem"
$env:PYTHONPATH = "$root\fastmel-source-repo"
Start-Process -FilePath "$root\fastmel-python310-venv\Scripts\python.exe" `
  -ArgumentList "codes\main.py","--config","$root\local-configs\wikimel_local.yaml" `
  -WorkingDirectory "$root\fastmel-source-repo" `
  -RedirectStandardOutput "$root\setup-logs\train-wikimel-full.out.log" `
  -RedirectStandardError  "$root\setup-logs\train-wikimel-full.err.log" `
  -WindowStyle Hidden -PassThru
```

**`Start-Process` cannot send both streams to one file, and the run splits across
them in a way that is easy to misread:**

| Stream | Carries |
|---|---|
| `.out.log` | Lightning's own progress bar — `Epoch N:`, `Validation:`, the final metrics table |
| `.err.log` | everything tqdm — `PreProcessing`, `UpdateEmbed` |

So a `.err.log` that appears frozen usually means the run is *training*, not stuck.
Watch both:

```powershell
Get-Content "$root\setup-logs\train-wikimel-full.out.log" -Wait -Tail 5
```

To merge the streams instead, run it in the foreground under Git Bash with
`2>&1 | tee`, the way the smoke test was logged.

### Measured runtime — budget more than the paper suggests

The paper reports 20–30 min for a full run on an A100 40GB. That is not what the
shipped code does on this machine, and the gap is structural rather than a GPU
difference.

`on_validation_start()` calls `_update_entity_embeds()`, which re-embeds the
**entire** knowledge base — every epoch, for validation *and* test. For WikiMEL
that is 215 batches of 512, and `limit_val_batches` does not shrink it: capping
validation to 4 batches still pays the full embedding cost first.

**This recomputation is necessary, not wasteful.** There is a single shared
`self.encoder` for both mentions and entities, nothing is frozen
(`configure_optimizers` puts every `named_parameter()` into AdamW, CLIP backbone
included), so each training epoch invalidates every stored entity embedding.
Caching them across epochs would score fresh mention embeddings against stale
entity ones.

Measured on the RTX 4090 with the smoke config (`num_workers: 0`), over two runs:

| Phase | Rate | Cost per eval phase |
|---|---|---|
| training | ~1.6 it/s @ batch 16 | negligible |
| `UpdateEmbed`, warm, `num_workers: 0` | ~2.4–2.7 s/it × 215 | ~9.5 min |
| `UpdateEmbed`, cold, `num_workers: 0` | ~4.0–4.9 s/it × 215 | ~16 min |
| `UpdateEmbed`, `num_workers: 4` | ~1.5 **it/s** × 215 | **~2.4 min** |

The second run was the same config on the same machine and came in ~40% faster;
the probable cause is the OS page cache holding the ~2.4 GiB of `kb_image` after
the first pass. That is unverified — assume the cold figure for the first eval
phase after a reboot. Full detail in §6 of the setup report.

The bottleneck is the CPU-side collate path, not the GPU. On a 300-image sample of
`WikiMEL/kb_image` (measured cold):

* the images are **already pre-resized to 384×384, ~23 KB** by the MIMIC authors
* decode + LANCZOS resize costs 3.8 ms each → ~7 min per 110k pass, single-threaded
* that is ~44% of the cold 16 min; the remainder is CLIP normalization,
  `tokenizer.pad`, tensor stacking, and the ViT-B/32 forward

Since nearly all of that happens inside `collate_fn`, it is what `num_workers`
parallelizes — which is why the full configs use `num_workers: 4`. Pre-resizing
the images on disk would *not* help; they are already small.

Practical consequence: with validation every epoch, a 30-epoch run spends far
more wall-clock in `UpdateEmbed` than in training. `EarlyStopping(patience=3)` on
`Val/mrr` in `main.py` will usually stop well before epoch 30. To cut it further,
raise `num_workers` or set `check_val_every_n_epoch: 2`.

TensorBoard logs land in `fastmel-source-repo/runs/<run_name>/`.

### Things to watch for

* **`num_workers` on Windows — needs the `__getstate__` patch.** DataLoader workers
  use spawn, and this repo's `collate_fn` is a bound method of
  `DataModuleForMIMIC`, so each worker pickles a full copy of the DataModule. Two
  consequences:
  1. Without the patch in `dataset.py`, **`num_workers > 0` cannot run at all**.
     The pickle reaches `trainer.fit_loop._data_fetcher.batch_to_device`, a closure
     inside `FitLoop.advance`, and dies with `AttributeError: Can't pickle local
     object`. `__getstate__` drops the `trainer` back-reference to fix it.
  2. Even patched, each worker holds the preprocessed KB (~110k–160k entities),
     ~1.7 GB resident per process. Upstream's 8 workers is a lot of RAM; local
     configs use 4 (~10 GB total with the parent), and the smoke config uses 0.
* **Missing images fail silently.** `choose_image()` wraps everything in a bare
  `except:` and substitutes `torch.rand((3,224,224))`. If the image folders are
  wrong, training will *run* and produce quietly terrible numbers rather than
  crash — nothing warns you. Guard against it before every run:

  ```powershell
  python mimic-image-downloader\verify_image_coverage.py --all
  ```

  It resolves filenames with the exact same rules as `choose_image()` (including
  the `split('/')[-1].split('.')[0] + '.jpg'` rename applied to mention images)
  and reports the hit rate for `kb_img_folder` and `mention_img_folder`. Add
  `--full` to check every record rather than a 4,000-item sample. Anything below
  ~99% means the paths are wrong.
* **`deterministic=True`** is hardcoded in `main.py`. Under torch 2.0 some CUDA
  kernels have no deterministic implementation and will raise; if that happens,
  the fix is `torch.use_deterministic_algorithms(True, warn_only=True)`.
* **Hard-negative mining differs from the paper** (already noted in the survey):
  the collator samples from the precomputed candidate list rather than re-mining
  top-10 BM25 per step.
* **Table 4 ablations are not reproducible as-is** — the `mean-attention`,
  `cross-attention`, `cross-attention-mlp` and `learned-attention` branches in
  `model_pooling.py` reference classes that exist nowhere in the repo.
