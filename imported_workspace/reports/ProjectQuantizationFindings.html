Process Followed

The project followed a progressively tighter loop: clean the benchmark, instrument the system, isolate tensor targets, combine the winning settings, then sweep chunk sizes for the smaller-GPU story.

Clean the evaluation target

Audited WikiMEL leakage, removed split/image overlap, and switched all comparisons to the no-leak checkpoint and config.

Measure the right deployment metrics

Defined accuracy, cache size, disk size, latency, throughput, subprocess timing, rank stability, quantization error, and GPU memory metrics in SmallerCheapGPU_MetricsPlan.md.

Target the largest repeated entity-side tensors

Focused first on entity_text_tokens, because it occupies 8591.88 MB of the fp32 cache and feeds the expensive TGLU path.

Run isolated tensor sweeps

Tested text tokens across fp32, int8, int6, int4, int3, and int2; then tested image patch tokens fp32 vs int4.

Combine text and image compression

Quantized both local token tensors to int4 while keeping text_cls and image_cls in fp32 to protect global matching and fusion calibration.

Sweep chunk sizes

Compared fp32, text-token int4, and text+image int4 at chunk sizes 1000, 2500, 5000, 10000, and 20000. The 40000 run was stopped because it was too slow and unnecessary after the 20000 behavior was clear.

Why text tokens matter

The fp32 entity cache is dominated by text tokens: 8591.88 MB out of 10860.67 MB. Compressing them attacks the biggest repeated inference artifact.

Why int4 is the conservative claim

Int3 and int2 look surprisingly strong, but int4 is easier to defend: no H@1 loss, stable MRR, large transfer reduction, and 1.77x speedup.

Framework Story

The project is no longer just a quantization result. It is a prototype for a resource-aware inference planner.

What the framework does now

Profiles fp32, quantizes selected cache tensors, measures accuracy deltas and deployment metrics, compares modes, and recommends a chunk size for a memory budget.

Where the max gains are

The max gains are in cache footprint, disk size, transfer time, and throughput. Peak matcher memory needs a second phase: tiled or quantized matcher computation.

Caveats And What Not To Overclaim

The results are strong, but the credible story depends on being precise about what has and has not been proven.

No fixed-chunk VRAM win yet

At the same chunk size, peak eval allocation is nearly identical across fp32 and int4. Current quantization compresses stored caches, not the full matcher working set.

20000 chunk is pathological

The mixed int4 20000 row took 2558.70 seconds and should be treated as an anomalous non-recommended operating point.

Needs transferability evidence

To sell this as a general framework, it needs at least one adjacent workload beyond this exact WikiMEL setup.

Recommended Next Steps

The next work should make the result repeatable, product-shaped, and transferable.

Repeat the headline rows

Re-run fp32, text-token int4, and text+image int4 at chunks 5000 and 10000. This turns the current best result into a stable claim.

Build the hardware-budget recommender

Input a memory budget such as 4 GB, 6 GB, or 12 GB. Output tensor modes, chunk size, expected H@1/MRR movement, runtime, QPS, and peak VRAM.

Add one adjacent workload

Run the same framework on text-only entity linking, image-text retrieval, reranking, or another entity linking dataset to test transferability.

Attack matcher memory directly

Implement tiled or quantized matcher computation so the system avoids materializing large fp32/dequantized tensors at once.

Prepare paper-quality diagnostics

Add rank-flip examples, top-k overlap, entity-type slices, ambiguous-name slices, and visually grounded slices.
